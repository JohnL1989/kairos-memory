# Kairos 威胁模型与安全对抗

> **文档定位：** 系统威胁模型分析。安全红线（S-01~S-19）的详细需求/实现/验证见 [docs/security/security-specification.md](security-specification.md)。高层定义见 [docs/foundation/architecture-v0.1.0.md](../foundation/architecture-v0.1.0.md) §8。本文件为 STRIDE 映射的完整展开。

---

## 一、攻击面分级

| 等级 | 描述 | 覆盖措施 |
|:----|:-----|:--------|
| **L1（本地进程）** | 同机进程攻击 API | API Key 认证与三级权限（S-01 启动缺 Key 拒绝 / S-06 越权拒绝）+ 限流（S-02） |
| **L2（同网段）** | 同网段设备尝试访问 | 127.0.0.1 绑定（S-04）+ admin Key 限制（S-08） |
| **L3（MCP Bridge stdio）** | MCP Bridge 通过 stdio 通道运行子进程，子进程可访问本地文件系统和进程环境 | 子进程运行于受限系统账户（S-04 同机绑定）+ 不继承父进程环境变量中的密钥（启动时通过专属环境变量传递仅限于 bridge 上下文的参数） |
| **L4（LLM 供应商）** | 调用 LLM 时的数据外泄 | 敏感信息脱敏（S-07）+ 按需发送不批量导出 |
| **L5（供应链）** | 第三方依赖包、本地模型权重文件、迁移脚本在获取或更新环节被替换 | 依赖锁定 + 模型工件校验 + 依赖审计（见 §三a） |

## 二、STRIDE 映射

### 风险评分矩阵

每条威胁按 **可能性（1-5）** × **影响（1-5）** 评分，总分 1-25：

| 等级 | 总分 | 响应 |
|:----|:----|:-----|
| **Critical** | 15-25 | 必须修复后方可发布 |
| **High** | 10-14 | 必须在发布前制定缓解方案 |
| **Medium** | 5-9 | 接受或记录在案 |
| **Low** | 1-4 | 接受 |

### STRIDE 映射表

| 威胁类型 | 攻击面 | 可能性 | 影响 | 总分 | 受影响组件 | 防护措施 |
|:--------|:-------|:------:|:----:|:----:|:----------|:--------|
| **Spoofing** | API Key 伪造 | 2 | 4 | **8(M)** | API 层 | PBKDF2 哈希 + 三级权限（S-01/S-06） |
| **Tampering** | 记忆内容篡改 / 注入 XSS | 2 | 3 | **6(M)** | 写入路径 + 导出路径 | S-09 常驻契约注入扫描（prompt injection / 角色劫持 / 后门 / 隐形 Unicode）；S-07 写入时敏感模式检测与 AES-256-GCM 加密（防敏感数据篡改落库） |
| **Repudiation** | 操作抵赖 | 1 | 3 | **3(L)** | 写入路径 | 审计记录每次变更的操作者/时间/content_hash（S-16 定向遗忘留痕）+ 结构性反例 P6 审计日志强制留存（S-17） |
| **Information Disclosure** | 敏感信息通过 LLM 调用泄露 | 3 | 4 | **12(H)** | 搜索路径 + LLM 调用 | S-04 本地绑定 + 按需搜索不跨路径 + 临时契约不写回；**S-07 敏感信息脱敏与导出保护（导出默认脱敏+截断，`?clearance=export` 掩码后截断前 200 字符，防 LLM 调用泄露）** |
| **Denial of Service** | 大量写入耗尽存储 | 2 | 2 | **4(L)** | API 写入路径 | 写入限流分层：单客户端建议 ≤60/min（S-02，令牌桶，约 1 ops/s），系统级硬上限 500 ops/s（熔断，S-02）。系统级容量目标 ≥100 ops/s（多客户端并行）。单条内容上限 64KB（S-03 超长输入拒绝）。说明：客户端级限流与系统级容量不矛盾，详见 [ops/configuration.md](../ops/configuration.md) §7 限流声明 |
| **Elevation of Privilege** | 越权执行管理操作 | 1 | 5 | **5(M)** | 管理端点 | admin Key 三级权限（S-06/S-08） |

## 三、LLM 特有攻击

| 攻击 | 场景 | 防护 |
|:-----|:-----|:-----|
| 提示注入致令牌耗尽 | 恶意 prompt 反复触发 LLM 调用 | 单次调用成本上限 + 日预算上限（单次调用成本上限与熔断参数见 [configuration.md](../ops/configuration.md) `KAIROS_LLM_MAX_COST_PER_CALL_FEN` / `KAIROS_LLM_CIRCUIT_BREAK_*`） |
| 适配器 SSRF | Embedding/LLM 端点 SSRF | 出站 URL 白名单（`KAIROS_SSRF_ALLOWED_HOSTS`）+ 解析后二次 IP 校验（`KAIROS_SSRF_IP_CHECK`、阻断指向内网/元数据服务的请求）+ DNS 重绑定防护（`KAIROS_SSRF_DNS_REBIND_PROTECTION`） |
| prompt 泄露 | 生成内容含敏感系统提示 | 敏感信息打标，LLM 输出不包含系统提示 |
| 成本炸弹 | 大量小请求累积日预算 | 单 run 成本熔断 + 日累计上限（重试计入同一次 run，不额外叠加） |
| Judge 漂移 | LLM-as-Judge 评分偏离标准 | 黄金集回归 + 漂移告警（黄金集回归用例待 test-plan 补充，见 [test-plan.md](../quality/test-plan.md) 预留测试用例编号表） |

## 三a、供应链攻击（L5）

> 记忆系统在本地运行三个模型底座（BGE-M3 嵌入 / intent-t5 意图 / timestamp-t5 时间抽取，见 [technology-stack.md](../development/technology-stack.md)），模型权重与 Python 依赖构成独立于 API 层的攻击入口——被污染的嵌入模型可系统性扭曲全库检索排序，且不触发任何 API 层红线。

| 攻击 | 场景 | 防护 |
|:-----|:-----|:-----|
| 依赖包投毒 | PyPI 依赖被替换/抢注（typosquatting），或传递依赖引入恶意代码 | 依赖锁定（lock 文件全量固化 + 哈希校验）；依赖树在发布前执行漏洞扫描；新增直接依赖须经 [technology-stack.md](../development/technology-stack.md) 选型表登记（未登记依赖不得进入构建） |
| 模型权重替换 | 本地模型文件（BGE-M3 等）在下载或更新时被中间人替换 | 首次拉取记录权重文件 SHA-256 摘要并落盘；每次加载前比对摘要，不匹配则**失败关闭**（拒绝启动，而非降级运行）；模型来源限定为已登记的下载源 |
| 迁移脚本篡改 | DB 迁移脚本被替换，在 `kairos db migrate` 时执行任意逻辑 | 迁移脚本纳入版本控制与代码评审；迁移执行前校验脚本摘要；迁移失败回滚（对齐 TC-A07-002） |
| 构建产物替换 | 分发包在发布通道被替换 | 发布产物签名 + 校验和随发布公告发布（见 [release-guide.md](../governance/release-guide.md)） |

> **v0.1.0 落地状态**：上述四项为**设计要求**，其中依赖锁定与迁移脚本评审在 v0.1.0 交付范围内；模型权重摘要校验与产物签名的实现排期见 债务 D-439。

## 三b、记忆投毒与侧信道

> 记忆系统特有威胁——攻击目标不是"读取数据"而是"让系统记住错误的东西"。这类攻击绕过传统机密性/完整性边界：写入的内容本身是合法的，危害在于其被长期保留并影响后续决策。

| 攻击 | 场景 | 防护 |
|:-----|:-----|:-----|
| 记忆投毒（长期偏置注入） | 攻击者持续写入语义一致的偏颇内容，使其在升华管道中被去语境化为"通用规律"，污染后续所有相关检索 | `provenance` 列 NOT NULL（S-15 来源缺失写入拒绝）——所有记忆可溯源；升华产物不得由单一 provenance 来源独占（蒸馏输入多样性校验）；`internal_inference` 来源不得自动提升为见证锚定（S-13 模拟产物转正拒绝） |
| 见证锚定伪造 | 通过高频使用制造"高价值"假象，使伪造内容进入身份注册表 | S-14 权重写回见证阻止（内部使用权重不得反向写回见证锚定）+ S-11 自校准修宪拒绝（内部信号不触发宪法修订端口） |
| 结构性反例滥用 | 将垃圾内容标记为 `is_structure=true` 以豁免遗忘，实现存储占位 | `structural_value` 升档条件为客观可验证判据（≥2 条 causal 引用 / 外部校准标记，见 [data-model.md](../specification/data-model.md) `structural_value`）；手动标注写入审计日志并计入 S-17 告警 |
| 检索侧信道（存在性推断） | 通过对比检索延迟或结果计数，推断某条被抑制/软删除记忆是否存在 | 抑制与软删除在检索层为**统一过滤**（`is_deleted=FALSE` + status 过滤，见 [data-model.md](../specification/data-model.md) `is_deleted`），不返回"存在但不可见"的区分性错误；错误响应统一为 `404`（`ERR-DB-004`），不区分"不存在"与"无权访问" |
| 审计日志侧信道 | 从审计日志的条目密度反推被抑制内容的敏感度 | 审计日志访问限 admin（`GET /v1/audit-log`）；日志字段以 `content_hash` 承载内容，不落原文 |

> **残余风险声明**：定时侧信道（timing side channel）在 v0.1.0 **不做常数时间保证**——本地单用户部署下攻击者已具备本机权限，此路径的边际收益低于实现成本。若后续支持多租户部署，须重新评估（见 债务 D-439）。

## 四、安全红线映射（补充）

以下安全红线的威胁场景在当前 STRIDE 映射中未展开（S-16/S-17 已在 §二 Repudiation 行挂名，本表补充其威胁场景细化）：

| 红线 | 威胁场景 | 对应攻击面 | 防护措施 |
|:-----|:---------|:----------|:---------|
| S-05 | 启动时密钥生成无盐值，彩虹表攻击可预计算 | CLI 启动流程 | 启动时检测盐值存在，无盐值拒绝启动 |
| S-10 | 见证豁免记忆被遗忘调度器清除，身份连续性丢失 | 遗忘调度器 | 见证豁免记忆不入遗忘候选池，测试验证不可绕过 |
| S-11 | 元认知自校准误修改宪法级偏好 | 元认知层治理器族 | 外部校准端口接收校准信号，**宪法修订端口**为修改宪法级偏好的唯一合法入口（见架构 §1.2 组件表——两端口为不同组件，本行防护措施与架构 §1.2 口径一致）——自校准不可修改宪法级偏好 |
| S-12 | 探索活动成本被计入使用价值排序，扭曲使用价值评估 | 策略层调节器 | 探索预算独立于使用价值排序，token/时间成本不计入使用评估 |
| S-13 | 模拟隔离区产物未经实证即进入存储层 | WM 层模拟隔离区 | 模拟产物须经实证印证后方可合并，写入时标记 provenance 检查 |
| S-14 | 使用权重变化反向写回见证锚定，使用频率冒充真实性 | 差异检验合并路径 | 使用权重永远不能反向写回叙事自洽度或见证锚定主副本，受差异检验强制执行 |
| S-15 | 记忆缺少来源分类，无法区分外部校准与内部推演 | 写入路径 | 每条记忆必须记录来源类型，来源缺失返回 422 |
| S-16 | 定向遗忘未留痕视为未执行 | 宪法解释层授权流程 | 所有定向遗忘操作写入审计日志，标记 `directed_forgetting` 或 `identity_demotion` |
| S-17 | 结构性反例免于遗忘 | 遗忘调度器 / 压缩管道 | P6 闸门守护——反例类记忆不受遗忘调度器评估，结构反例在压缩/升华管道中强制保留；对 is_structure 记忆的定向遗忘操作被宪法主权面拒绝并告警（架构 §8 S-17 两层语义）。**法定擦除例外**：法定擦除请求命中 is_structure=true 记忆时改由 S-19 哈希净化执行（保留结构位点），经宪法解释层单独裁定 + statutory_erasure 留痕（架构 §8 S-17 R20-05 例外） |
| S-18 | Hard Delete 安全门 | 存储层/向量存储 | 硬删除须先确认对应 vector 已清理完毕，才允许 SQLite/PostgreSQL 数据删除。软删除不受此限。强制执行 fail-closed：vector 清理失败则事务回滚，数据保留 |
| S-19 | 哈希净化（Hash Purification） | 遗忘调度器 | 定向遗忘的记忆用 SHA-256 替代原文（化石节点），保留拓扑关系但不可恢复原文。GDPR 擦除请求对应 S-19 执行 |

## 五、审计完整性

审计日志使用双字段链式签名防止篡改——明文 content_hash 链供按内容追踪，HMAC-SHA256 链供完整性校验：

```text
日志条目 N:
  # 双字段链：明文 content_hash 链 + HMAC 完整性链
  prev_content_hash = previous_entry.content_hash  # 明文链，供精确定位
  plaintext = timestamp + operator + action + content_hash + prev_hmac  # prev_hmac 来自上一条
  hmac = HMAC-SHA256(hmac_key, plaintext)
  # 存储：entry.content_hash + entry.hmac + entry.prev_hmac + entry.prev_content_hash

校验：
  逐条重算 HMAC 并与存储值比对
  链式校验：条目 N 的 previous_hash == 条目 N-1 的 hash
```

- HMAC 密钥（`KAIROS_AUDIT_HMAC_KEY`）与 API Key 物理隔离存储（轮换周期与旧密钥保留策略见 [security-specification.md](security-specification.md) §5 密钥管理）
- 审计日志的存储位置与数据存储物理隔离（独立表或独立文件）
