## 内容提炼
### 核心论点
1. OpenClaw 默认设置把全部内容塞进记忆文件，既让智能体困惑又增加 API 成本——每次请求读庞大文件会迅速消耗大量 token，多数人默认接受并反复粘贴上下文、重复解释项目，其实完全没必要（00:07 / 00:14 / 00:25）
2. 上下文窗口 = 短期记忆：窗口内内容智能体都能看到，会话一结束窗口关闭、那次对话的上下文消失；当作持续协作者（研究助理）使用时必须在不同会话之间记住项目、偏好、已做决定、已收集数据（00:54 / 01:06 / 01:19）
3. 不必局限于单一记忆方案：优秀配置应组合 2-3 种方法，分别处理不同性质的信息（短期窗口 + 中期对话记忆 + 长期结构化数据 = 完整记忆架构）（10:08 / 10:25 / 10:48）
4. 「有意识的记忆设计」比「把所有东西扔进数据库然后指望检索起作用」得到更好的结果——你决定哪些内容值得被记住（03:04 / 03:10）

### 关键机制
- 方法一：结构化记忆文件夹（markdown 文件，约 60 秒可设）：项目目录建记忆结构——主记忆文件夹（`goals.md` / `decisions.md` / current `status.md`）+ 偏好设置（coding `style.md` / communication `preferences.md`）+ 知识库（research `notes.md` / `reference.md`）；关键是写进自定义指令/系统提示词：告诉 agent 每次会话结束时更新记忆文件中的相关文件。三大优点：完全透明无黑箱（可直接查看 agent 记住了什么）、支持 Anthropic/OpenAI 等主流或本地模型、你掌控结构（01:34 / 01:54 / 02:28 / 02:43）
- 方法二：内置 memory search（记忆搜索）：设计目的是让 agent 在存储的记忆、过去对话、保存的上下文中搜索；但底层使用 OpenAI/Gemini/Voyage 的嵌入模型，需要相应 API key 才能运行且默认关闭——若只把 Claude 当主模型，记忆搜索会「悄无声息的失败」（不报错但什么都不记住）；需在设置里为嵌入模型单独配置 API key（不一定要作为主模型）(03:21 / 03:52 / 04:08 / 04:48 / 05:17)
- 方法三：Mem0 第三方插件：自动三步——监控每次对话、提取真正重要的信息（偏好/决策/事实/项目细节）以向量嵌入形式存储、在每次对话开始时或上下文相关时检索正确记忆注入上下文，全程自动；代价是依赖第三方（数据可能经过 Mem0 基础设施，需读隐私政策）、可能提供无关记忆或漏掉该捕捉的内容（05:52 / 07:03 / 07:32 / 07:44）
- 方法四：SQLite 数据库：OpenClaw 原生可读写 SQLite（无需插件、无需额外 API key）；适合密集结构化数据（上百 API 端点、产品目录、客户记录、多字段研究数据、跨季度财务数据）；markdown 处理这类数据会崩溃，向量检索适合模糊检索但精确查询（「列出所有用 POST 且需要认证的端点」）是 SQL 的强项；自然语言查询由 agent 转成 SQL 执行（08:20 / 09:04 / 09:17 / 09:19）
- 组合架构：结构化文件夹（高层次上下文和偏好设置）+ Mem0/记忆搜索（会话间对话记忆）+ SQLite（需精确查询的密集结构化数据）= 短期（上下文窗口）+ 中期（Mem0/记忆搜索）+ 长期（SQLite）的完整记忆架构；SQLite 是单个 DB 文件，便携持久、重置后保留、可版本控制（10:08 / 10:25 / 10:37）

### 可操作细节
- 四方法适用场景：结构化文件夹=快速入门/完全透明/适用任何 LLM；记忆搜索=OpenClaw 内快速自然语言回忆（注意需 OpenAI/Gemini/Voyage key）；Mem0=自动化长期检索与维护型对话记忆（一劳永逸选择）；SQLite=需要精确查询的高密度结构化数据（10:55）
- 升级路径建议：今天先花约 5 分钟从方法一开始，再按使用场景加 Mem0 或 SQLite，并确保记忆搜索用正确的 API key 配置（11:30）
- 嵌入调用成本极低（「几分钱都不到」），不要因多要一个 API key 而放弃（05:17）
