## 内容提炼
### 核心论点
1. 痛点本质：每个 AI 编码 Agent 会话之间都是无状态且彼此孤岛的——「你不是在跟一个记性差的助手合作，你是在跟一堆互相不通话的助手合作」（00:27-00:49）。
2. Memorix 的定位：开源跨 Agent 记忆层，通过 MCP 协议接入已有 AI 编码工具；记忆不放在聊天窗口里、不绑在某个工具里，而是挂在 Git 项目根目录下——「Agent 可以换，项目记忆不变」（00:51-01:17）。
3. 记忆不只存「发生了什么」，更存「为什么这么做」：「数据库配置改了」几乎没价值，「为什么选 PostgreSQL 而不是 MongoDB」才是真正值钱的记忆——前者是事实，后者是决策理由，Memorix 专门为后者设计了一整层（01:45-02:14）。
4. 代码记忆新鲜度检查：如果一条记忆指向的那段代码后来被改过了，Memorix 不会假装它还成立，而是把这条记忆标记成「可疑」或「已过期」——解决记忆系统「你越用越信它，结果它悄悄拿过时信息误导你」的老毛病（02:49-03:16）。

### 关键机制
- 四层记忆各管一类问题：第一层观察记忆（存事实、坑修复、实现笔记，回答「这东西怎么工作的」）；第二层推理记忆（存决策理由、备选方案、约束和风险，回答「我们当初为什么这么选」）；第三层 Git 记忆（把每次 Commit 变成可搜索的工程事实，回答「改了什么、在哪、为什么重要」）；第四层代码记忆（把记忆和文件符号绑定，回答「我该先看哪段现有代码」）（02:16-02:44）。
- Memory Autopilot（默认入口）：一条命令「memorix context + 任务描述」，根据任务类型生成定制简报——修 Bug 偏向测试和复现路径、发版偏向 Changelog 和构建检查、新人上手偏向文档和入口文件；不相关的记忆会被单独放进「警告车道」，不会污染主上下文（03:20-03:49）。
- 接入方式：一条命令「memorix setup + Agent 名字 + Global」，按每个工具原生支持的方式安装（装插件/写 MCP 配置/挂 Hooks）；默认只暴露 7 个精简工具，不撑爆 Agent 的工具列表；「别人是 SDK 要你写代码集成，它是即插即用」（03:53-04:19）。
- 本地优先架构：SQLite 做权威存储、Orama 做搜索，数据全在本地；即使不配任何大模型 key 也能用本地全文检索工作；可接 OpenAI/OpenRouter embedding 提升语义质量但是可选项——「没有云依赖，数据不出你的机器」（04:53-05:20）。
- 附赠组件：Mamcode（终端编码 Agent，读写同一份 Memorix 记忆）+ Orchestrate 命令（协调多个 Agent 并行干活：任务交接、文件锁、验证门、Review 循环，多 Worker 时自动建 Git Worktree 再合并回来）——「这已经不只是个记忆库了，更像一个本地的 Agent 控制台」（04:22-04:48）。
- 风险自述（作者在仓库放了中文的「待预知问题与路线图」文档）：多 Agent 同时写入曾破坏数据完整性（已修）；未修——Git 项目 ID 基于目录名，换台机器换个路径 ID 就变、记忆就对不上；设计取舍——标称高价值（Decision）记忆永不过期，时间长了可能膨胀（05:21-06:02）。

### 可操作细节
- 适用判断：如果每天在两三个 AI 编码工具之间来回切、受够了反复解释同一个项目、又不想把代码上下文传到别人云上，值得花十分钟试一把；如果只用一个工具且项目不复杂，四层记忆是杀鸡用牛刀（06:56-07:15）。
- 两个门槛：①五个月的项目单人维护却要兼容 14 个以上工具，兼容矩阵维护压力大、边缘工具成熟度参差；②本地 embedding 模型（FastEmbed）首次要下载约 30MB，国内网络容易超时，想用更好的语义能力还得接海外 API（06:02-06:22）。
- 记忆挂载点：Git 项目根目录，而非聊天窗口或工具配置（01:05-01:17）。
