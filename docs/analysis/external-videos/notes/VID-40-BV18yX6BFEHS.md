## 内容提炼
### 核心论点
1. Zep 解决的四大痛点：①长期记忆难——对话越长越贵、token 耗费越多、容易漏掉关键信息；②跨线程（跨会话）不连贯——A 会话说过的话 B 会话不记得；③业务数据与对话脱节——CRM/订单/工单/设备等业务数据不在聊天记录里，需要大量 code 才能融合进上下文；④**事实会变化**——地址/套餐/状态会变，把旧信息一直塞给大模型会被旧事实误导（P1 00:05-02:37）
2. 三层架构：数据写入层（对话消息 + 业务数据统一写入）/ 知识层（每个用户一张**随时间变化的知识图谱**：实体=节点、事实+关系=边，且带**时间属性——什么时候有效、什么时候失效**）/ 上下文装配层（ContextBlock）（P1 02:59-05:05）
3. ContextBlock 装配逻辑：基于最近消息切片去**全量用户图**中找相关内容（不需手动查询）；输出 = 用户摘要 + 一组带时间范围的事实列表；**跨会话可用**——传入 session ID 仅用于判断「此刻的相关性」（P1 04:52-05:37）
4. 工程接入四步：创建用户 → 每会话一个 session ID → 每轮 add_message 写消息（注意顺序）→ 取 ContextBlock + 最近几条原始消息发给大模型（P1 05:55-06:55）

### 关键机制
- 业务数据写入：对话之外影响回答的事实（订单/订阅/账号状态/工单/产品使用等）通过 session、文本或 message 形式写入用户图（P1 06:58-07:21）
- 记忆面向「用户级」：每个用户一张随时间演化的知识图谱，图含实体（人名/物品/类别）与关系（P1 04:05-04:27）
- P2 实例细节：官网 app.getzep.com 注册 → 创建 project 取 API key（免费版限制两个项目）→ pip 安装 SDK → 创建用户（user ID/email/姓名）→ 添加用户简介（输出语言/沟通方式/偏好/限制）→ 构建 context 模板（模板 ID + 用户画像 + 知识图谱，**最多 6 个节点 12 条边**）→ 创建线程（session）→ 写第一轮对话 → 取回 context block（P2 00:13-06:55）
- context block 输出示例：用户画像（中文）、用户 ID、姓名、邮箱、地址、关键事实列表、关键实体（如「张三，类型=用户」）（P2 06:15-06:45，from 371-407）

### 可操作细节
- 用户画像字段：输出语言（如中文）、沟通方式（电话/邮件/工单/App）、偏好信息、限制（P2 03:50-04:29）
- 知识图谱规模上限：6 节点 / 12 边（P2 04:34-05:17）
- 消息写入顺序必须正确（用户消息 + 助手消息按发生顺序）（P1 06:20-06:35，from 388-390）

## 存疑与未验证
- 视频为 Zep **云平台（Cloud）**使用口径，与 REPO-07 实证的 Zep 社区版（Go）+ Graphiti 引擎不同轨：视频未提 Graphiti，也未展示引擎内部（未验证引擎与云平台一致性）
- 「MacroFish」为 UP 主引入语中提到的热门开源项目（称能预测未来、融资几千万），名称转写可能不准，未验证
- 「免费版限制两个项目」「每月额度」为 UP 主演示时口述，属时点状态（未验证）
- P2 演示的具体 SDK 包名（转写为 dapclaw=zep-sdk?）、API 参数名为屏幕演示转述，未逐字核对（未验证）
- 知识图谱「6 节点 12 边」上限为演示时 UI 显示，未验证是否为产品固定约束
- 视频未提及 Zep 的遗忘/衰减机制（REPO-07 实证 Graphiti 有四时间字段），本笔记未把「遗忘」记为 Zep 理念（视频未讲，不虚报）
