## 内容提炼
### 核心论点
1. 三个真实事故（修正记录埋在 650 行而 agent 只读前 200 行导致重复犯已修三次的 bug；System Prompt 塞 15 条偏好+10 段上下文导致最重要的「不要删」指令被淹没；三个月前的旧配置记录导致生产事故）指向同一真相：「你不是缺记忆，你的记忆系统正在杀死你的 Agent」（00:01-00:53）
2. LLM 先天失忆的三层认知：每次调用无状态；多轮对话靠把历史塞回输入（决定成本、速度和上限）；Lost in the middle——LLM 上下文表现 U 形曲线，开头结尾准确率高、中间断崖下跌（20 个检索文档约 4000 token 时中间位置准确率从 75% 降到 55%），源于 causal attention 的 attention sink + 混合训练目标的 recency bias；「200K token 窗口不表示 200K token 的有效记忆」（01:11-01:57）
3. 第一步不是装向量数据库，而是三分类：该扔的（能从外部重新推导的信息：文件内容/搜索结果/一次性中间输出，绝不存进记忆）/ 该缓存的（短期高价值：当前任务上下文/最近几步工具输出/本 Session 活跃状态，跟 Session 走、Session 结束就清）/ 该存的（不可推导的信息：框架切换决策、bug root cause、选型原因，丢了就没了）——「80% 的人第一步就错了，一上来就装向量数据库」（02:51-04:51）
4. 检索黄金法则：先用 FTS5 做廉价宽召回找到 3-5 条候选，再用 LLM 做昂贵的语义提炼判断哪条真正需要——「FTS5 负责快和宽，LLM 负责精和深」，解耦搜索和理解（07:04-07:25）
5. 过时记忆是毒药：每条记忆必须知道自己是活着的还是死了的——created_at / valid_until / superseded_by 三时间戳，不删除只标记 superseded，从而能回答「现在什么是真的」和「去年这个时候什么是真的」（07:26-09:02）

### 关键机制
- 上下文窗口实际消耗测算：System Prompt 500-2000 token、15 个工具定义 2000-5000、一次 RAG 检索 2000-8000、20 轮对话 5000-15000、30 步 agent 工作流轻松超 10 万 token——「上下文不是记忆，上下文是你花钱租的一个越来越挤的舞台」（02:04-02:30）
- Step 1 三分类工作表 + 搬家比喻：该扔=旧报纸过期优惠券；该缓存=牙刷睡衣（随身包）；该存=房产证学历证（丢了补办三个月）。真实踩坑：`memory.md` 从 200 行涨到 800 行，因为对话记录/临时决策/搜索结论全混在一起没有分类系统（04:14-05:23）
- Step 2 SQLite + FTS5 是第一块砖：虚拟表 + FTS5、按行写入、match 语句 + BM25 排序三步；支持关键词搜索/前缀匹配/布尔逻辑、无额外依赖、毫秒返回；agent 90% 的记忆查询是带精确关键词的（「上次那个 bug 怎么修的」——关键词是帧阶段、math.floor、audio continue tier 这类精确问题）；向量语义搜索适合模糊跨话题查询，不是每天需要（05:48-07:25）
- Step 3 三时间戳：created_at（何时产生）/ valid_until（何时失效）/ superseded_by（被哪条替代）；来自 Zep 时序知识图谱系统——「时间是一等公民」，其他记忆系统问「这段记忆相关吗」，Zep 能回答「这段记忆在第三季度时是真的，现在已经被推翻了」；真实踩坑：remotion 的 frameRange 参数改为 frames 参数后旧记录未标记过期，三个月后重构 agent 翻出旧记录、渲染全部失败、排障 40 分钟——「那条过时记忆比我预期的时间多活了整整三个项目」（07:36-08:58）
- Step 4 Frozen Snapshot 冻结快照（保护前缀缓存）：Anthropic cache_control 写入 +25% 成本、读取 -90%；OpenAI 自动前缀缓存 50% 折扣——但要求每次请求开头部分完全一样，「哪怕多一个空格，缓存失效」；真实踩坑：System Prompt 加动态日期变量导致前缀缓存从未命中、成本高 25%-75% 而缓存命中率指标多数人不看；Hermes 的 frozen snapshot 设计：Session 启动时冻结核心记忆（项目规则/个人偏好/前 800 token）到 System Prompt，临时信息放消息列表末尾不破坏前缀；两个修复策略——拆两段（头部冻结区放角色定义/核心规则/静态偏好，尾部动态区放 session 目标/临时约束/用户刚说的需求）+ 动态信息放整段提示词最末尾（即使换行前面的前缀仍命中）——「不改任何代码，缓存命中率从零拉到 60% 以上」；「这不是选修，这是生存刚需」（09:02-11:03）
- Step 5 归纳层（AutoDream 思想）：「不归纳的日志，不是知识库，是垃圾山」；归纳不需要实时（每天一次就够了），但不能不做；实操定时脚本：每天凌晨或 session 结束触发，读近 7 天日志做三件事——去重（多条记录同一件事）、冲突检测（互斥信息保留最新、标记旧为 superseded）、实效淘汰（超 30 天没被引用的降级为归档存储）；真实踩坑：5 条高度相似渲染崩溃记忆（ep06/ep08/ep25 不同崩溃事件）语义高度相似、修复方式各异，agent 输出混合三个 bug 修复方案的合成答案——「不是搜索引擎不准，是太准了」；「归纳层不是奢侈品，它是搜索精度的防火墙」（11:03-12:51）
- Step 6 按需接入向量库和知识图谱：查询模糊无精确关键词（用户反馈有没有提到类似情绪）时用向量库；事实频繁变更需记录「谁影响了谁、什么推翻过什么、因果关系」时用知识图谱（Zep 的 Graffiti 引擎：向量库之外加时序知识图谱，每个事实有 valid_at/invalid_at 时间戳）；「前置条件不满足就上向量库，你会得到一个更精致的垃圾场」；三种存储不是互斥，是分阶段介入（12:51-14:06）
- Step 7 验证：三个核心指标——指令遵从率（System Prompt 嵌入隐蔽规则如回复末尾加特定 token，注入大量记忆后遵从率不应下降，下降说明记忆注入污染了关键指令）；检索召回准确率（20 个已知答案问题测 top1 命中率，目标 80%+）；前缀缓存命中率（cache read tokens / total input tokens，目标 >80%，低于就是在烧钱）；五个测试用例——精确召回测试（上次那个 bug 怎么修的）/ 实效性测试（故意留 3 个月前旧框架记录，agent 能否识别过时）/ 性价比测试（删除 slashtmp 临时文件这种简单操作不应被记忆系统干扰，出错说明注入太多）/ 时间旅行测试（3 个月前做的决策还用吗——需同时理解当时约束和现在变化）/ 经济性测试（100 次请求后的缓存命中率）（14:07-15:50）
- 五条设计铁律：能从外部重新推导的信息绝不存进记忆；时效即架构（每条记忆必须有时间戳，过时信息必须能被自动降权）；（第三条字幕缺失）；前缀缓存优先（每次记忆注入的变动等于缓存失效等于成本爆炸，稳定内容前置、动态内容后置）；遗忘是能力（好的记忆系统知道该忘记什么）（15:51-16:55）

### 可操作细节
- FTS5 宽召回 + LLM 精提炼：候选 3-5 条（07:04-07:10）
- 三时间戳字段：created_at / valid_until / superseded_by（07:36-07:48）
- 前缀缓存：缓存写入 +25% 成本、读取 -90%；动态内容放提示词最末尾（09:13-09:18 / 10:49-10:57）
- 归纳频率：每天一次或 session 结束；读近 7 天日志；30 天未引用降级归档（11:33-11:57）
- 验证指标阈值：召回 top1 命中率 ≥80%；缓存命中率 >80%（14:45-15:05）
- 向量库/知识图谱接入判据：查询有无精确关键词、事实变更频率（12:53-13:28）
