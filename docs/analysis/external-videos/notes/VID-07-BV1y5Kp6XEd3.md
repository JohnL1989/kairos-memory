## 内容提炼
### 核心论点
1. 「向量数据库 + RAG 拼 Prompt」这一招在生产环境远远不够：Demo 看着完美，面对成千上万用户时 Agent 几轮就糊涂——真正上生产的系统必须解决三个关键问题：向量数据库能力边界、记忆分层（不同性质数据走不同读写路径）、时间维度上的状态一致性（00:11-02:30）
2. 向量数据库的两个典型失效模式：①精确查询失效——查手机号/订单号这类确定性信息，靠语义相似度检索会带出一堆「封面长得差不多」的干扰，注意力被带偏、数字念错甚至自编；②时间盲区——「我在上海工作」（半年前）与「我搬到北京居住了」（昨天）语义极接近，被一起检出，大模型分不清哪条最新，最后带着过期信息做决策（拿上海地址帮北京用户下单）（02:32-03:57）
3. 解法是「数据结耦 + 分层动态上下文管理」：四层记忆架构——会话元数据（内存、用完即弃、不持久化不污染后续对话）/ 用户结构化档案卡（JSON 或关系型存储，key-value 精确键值查找，完全绕过语义检索，从源头消除噪声）/ 近期对话摘要（轻量级模型定期压缩，几百字结构化摘要代替几千字原始上下文）/ 滑动窗口（只负责当下几轮原始上下文，超出行数或 token 上限按 FIFO 丢弃）（04:04-06:34）
4. 工程三件套保证状态一致性：原始账本（所有交互事实以事件形式单向追加写入、不允许修改删除，任何决策可原位回溯）+ 控制策略（规定何时读何时写，隐私/合规清除时不在底层账本删数据而是生成派生视图时过滤——保住审计痕迹）+ 派生视图（把流水账事件按当前任务需要聚合成大模型能看懂的结构，如用户状态档案卡，不同任务拉取不同视图）（06:36-07:50）
5. 双时间戳机制解决新旧信息时序冲突：每条事实数据打两个时间戳——写入时间（进入系统的物理时间）+ 有效时间（现实世界里的有效时段）；用户搬家时不是新增一条相似记录，而是把「居住地=上海」的有效时间截止、插入「居住地=北京」且有效时间从搬家时刻指向未来；模型读视图时系统始终按当前有效时间过滤——「模型拿到的永远只有当下唯一生效的那条地址，新旧信息打架在工程层面被彻底规避」（07:57-09:00）

### 关键机制
- 程序性记忆（skill 封装）：复杂流程任务（退款、申诉）完全依赖大模型在线零基础规划稳定性差，经常因某一步概率偏差导致任务卡死或走偏；做法是 Agent 多次成功跑通某类任务后，把交互轨迹和决策路径沉淀下来、把成功经验固化成标准流程（SOP 式 skill）——像给熟练员工发标准操作手册，动作不走样、错误率下降（09:07-10:10）
- skill 模块三要素：①标准任务（任务流转的确定性骨架，第一步做什么第二步做什么代码定死）；②必要参数（执行中从分层记忆提取所需变量，如用户 ID、订单状态）；③校验规则（运行步骤的前置条件和边界控制）（10:13-10:47）
- 整体协作闭环：四层分层数据（物理隔离，保证模型输入干净）→ 交互事实单向追加进原始账本（源头数据绝对安全）→ 读取时数据流进控制策略 → 双时间戳时序过滤 → 聚合成模型直接使用的派生视图 → 运行中发现成功路径就固化为程序性 skill 再输入到系统执行端（11:03-11:40）
- 收尾总结：「生产级 Agent 绝对不是拼谁上下文窗口更长、谁塞下更多原始对话——数据塞得越多噪声越大；高可靠性系统一定是在物理上做分层管理、在时序上做精准控制、在经验上做固化沉淀」（11:41-12:04）

### 可操作细节
- 四层记忆架构的分层读写路径：元数据→内存；档案卡→key-value 精确查找；摘要→定期压缩（轻量级模型）；滑动窗口→FIFO 丢弃（04:19-06:20）
- 双时间戳的工程语义：写入时间=物理入库时刻；有效时间=现实世界有效时段；读取时按「当前有效时间」过滤（08:01-08:46）
- 遗忘/注销的实现：用户要求注销或遗忘历史时，不在底层原始账本删数据（破坏审计痕迹），而是通过控制策略在生成派生视图时过滤——模型看不见，但保留可审计的物理日志（07:24-07:50）
- 程序性记忆的触发条件：「多次成功跑通某类任务之后」沉淀（09:41-09:51）；skill 挂载在推理节点上，触发特定任务时不再从头规划（10:13-10:23）
