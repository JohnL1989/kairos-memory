## 内容提炼
### 核心论点
1. 反直觉现象：上下文越长 Agent 未必越聪明，反而可能越容易被旧线索和错误假设拖住；长程 Web Agent（几十到几百轮交互）的瓶颈不在模型能力，而在「长程搜索的工作记忆」——搜索词、访问结果、失败尝试、中间判断在短任务是资产，长任务里可能变成噪声（00:07-00:31）
2. AgentSwing 不是发明一种固定的上下文压缩技巧，而是**把上下文管理变成一个状态相关的路由问题**：当前该保留摘要还是清空，要看各分支往前走几步后的真实表现（00:35-00:49）
3. 概率分解：任务成功 = 搜索效率 × 终端精度；无上下文管理效率高但容易被噪声影响（精度低），Discard All 判断干净但丢线索（效率低），Keep Last N 与 Summary 居中——但都是静态策略，从头到尾用同一种处理方式（01:29-02:20）
4. 两个案例证明「策略没有绝对赢家，状态才是关键」：Mando 案例中第 23 轮刚收到关键人物 Tupac 线索时 Keep-Last-N 分支赢了（清空丢突破口、摘要保留错误主假设）；Leave Crickets 案例中主线被无法抽取的 PDF 卡住、历史全是重复失败时 Discard All 分支赢了（03:14-04:23）

### 关键机制
- 前瞻路由（look-ahead routing）：上下文长度超过预设阈值时，不立即选一种压缩策略，而是同时生成多个分支（保留最近 N 轮 / 做摘要 / 全部丢弃只留原始问题）；每个分支继续与环境交互 K 轮（前瞻）；前瞻结束后模型看到这些候选延续和原始上下文，判断哪条路径最有希望，只保留被选中的主线（02:22-02:55）
- 为什么多走几步再选：只看压缩后的上下文很难知道它会带向哪里；多走几步后分支暴露真实后果——是继续卡在旧错误里、保住了新证据、还是成功从失败路径重启（02:57-03:12）
- 消融证据：随机选分支 51.0、无前瞻 50.0、K=1 为 52.5、K=3 达 60.0、K=5 又降到 55.0——K=3 是甜点：K 太小信号不够，K 太大可能触及上下文长度限制或让路由判断混乱（05:43-06:04）
- 与 AgentFold 的层级区分：AgentFold 更偏训练/模型能力层面的主动折叠（改模型内功），AgentSwing 是测试时外部控制框架（改运行时决策），不要求重新训练模型（06:22-06:39）
- 多样性要求：多种策略组合通常优于单一策略；若候选分支都只是相似程度的压缩，路由再聪明也难产生互补收益（07:33-07:49）

### 可操作细节
- 论文身份：Adaptive Parallel Context Management Routing for Long-Horizon Web Agents，阿里巴巴通译实验室（00:52-01:00）
- 实验：BrowseComp / BrowseComp-ZH / HLE（Humanities Last Exam）三基准；模型 GPT-OSS-120B、DeepSeek-V3.2、通义 DR-30B-A3B；工具主要是 search 和 visit，HLE 加 Google Scholar 和 Python（04:31-04:53）
- 代表数字：GPT-OSS-120B 在 BrowseComp 上无上下文管理 39.5 → AgentSwing 60.0；DeepSeek-V3.2 加 AgentSwing 在 BrowseComp-ZH 达 71.3、HLE 达 44.4；通义 DR 在 BrowseComp 达 60.5（04:55-05:18）
- 对齐分析（非多花计算换分数）：AgentSwing pass@1 41.8、平均 190.3 轮 vs Discard All 28.7、平均 297.2 轮——提升不是靠更多轮次硬堆（05:19-05:40）
- 工程代价：每次触发时多个分支都要前瞻几轮，顺时计算量更高；论文认为总开销相对可控（因为 AgentSwing 常用更少轮次完成任务），但低延迟场景仍需权衡（06:58-07:17）
- 限制：当前路由由 Agent 模型自己判断，模型判断能力就是路由上限；未来可用更强的专用路由器/验证器/轨迹评估器让分支选择更可靠（07:17-07:32）
- 收尾判断：长程 Agent 失败应拆成「效率×精度」两个维度看；上下文管理不是装饰功能，只优化单点压缩看不到真正的失败来源（06:41-06:58 / 07:52-08:06）
