## 内容提炼
### 核心论点
1. 极简 agent loop：用户消息→构建上下文（内部记忆+开箱即用提示词）→发送 LLM→工具调用循环（调用、执行、结果回传）→最终回复→记忆更新步骤（让智能体分析消息，看有没有值得记住并写入记忆的内容，从而在整个交互过程中学习）（04:04-07:25）。
2. 上下文 = 几个 markdown 文件的组合：`soul.md`（设定性格/语气/目标，刚安装时通常为空、用默认系统提示词替代）+ `user.md`（每当 Hermes 了解到用户新信息就自动更新）+ `memory.md`（任意记忆：工具使用方式、工作流、对话中学到的有趣内容，取决于 `soul.md` 设定的目标判断"值得记"）+ 过去会话摘要（仅配置外部记忆后出现）+ 技能/工具描述 + 最新消息（08:11-13:21）。
3. 上下文压缩：默认在上下文使用到 50% 时触发（可配置，小模型可设 70% 等）；两个检查时机——每轮调用 LLM 前用字符数近似估算、以及 LLM 返回上下文窗口错误时用 usage 参数累加；压缩 prompt 分多个小节（整体目标/约束/已完成操作/当前状态/历史进展/卡点/关键决策/相关文件/之前总结/下一轮要纳入的对话），比极简派的压缩 prompt 内容丰富得多（13:39-20:00）。
4. 网关：常驻异步 IO 循环轮询 telegram/discord/邮件/短信/whatsapp 等（各有不同轮询方式：webhook 或每秒小循环）；收到单条消息后从零构建上下文——通过会话 ID（网关名+平台会话 ID）从本地 sqlite 拉全部消息历史拼回对话；会话管理器按消息时机决定 interrupt / steer / 排队（20:55-28:04）。
5. 记忆三种形式：markdown 文件（始终追加在系统提示词之后）+ sqlite 数据库（存储每次交互的每条消息，含一个纯文本表专门做相似性搜索）+ 外部记忆提供商（mem0/supermemory 等，默认不配置，建议启用；外部记忆在会话第一条消息回复后才查询一次——模拟人类"回答完问题后回想过去相关对话"的方式）（28:30-34:45）。
6. 定时任务（cron）：每分钟运行一次的 tick 函数检查任务列表并执行；文档声称存 sqlite，但视频作者代码分析发现实际存在 hermes home 目录的 jobs.json（文档与实现不一致的实证发现）；每次运行记录存 output 目录下任务 id 命名的 markdown；cron 通知直接发往主消息平台而非走发送消息工具（34:57-39:59）。

### 关键机制
- 记忆更新步骤：回复后让智能体分析消息判断是否有值得记住的内容（价值判断主体是 LLM 自身，无外部规则）（06:46-07:23）。
- 压缩触发检查：轮前用字符数近似（成本低、够用），LLM 报上下文窗口错误时用响应 usage 参数精确累加（两者结合，不用 tokenizer 省成本）（16:37-18:20）。
- 外部记忆查询时机：第一条消息之后、智能体已了解用户意图后查询，试图猜测下一个问题——"像人类所做的那样"（32:56-34:03）。
- cron 通知路径：不调用发送消息工具，系统自动在"主平台"（设置网关时指定的用户 id）发通知（38:47-39:30）。

### 可操作细节
- 压缩阈值默认 50%，可配置为 70% 或其他值（14:16-15:26）。
- 上下文压缩器 prompt 位于 context_compressor 文件约 1400 行，分节结构含整体目标/约束/已操作/当前状态/历史进展/卡点/关键决策/已解决问题/相关文件/关键上下文/之前总结/要纳入的下一轮对话（18:38-19:33）。
- 消息历史存储：sqlite 会话 id = 网关名（如 telegram）+ 平台返回的会话 ID（24:58-25:54）。
- jobs.json 路径：hermes home 目录下，列出所有定时任务（含提示词与操作）（36:56-37:38）。

- 「context_compressor 文件约 1400 行」为视频画面中的行号，随重构可能变化（未验证）。
- 压缩阈值默认 50% 与 Hermes 实际默认配置（可能已随版本变化）未核对（未验证）。
- 视频为英文演讲的自动中文翻译转写，术语对应可能存在失真（未验证）。
