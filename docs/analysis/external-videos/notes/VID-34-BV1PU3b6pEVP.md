## 内容提炼
### 核心论点
1. 记忆不是模型内部机制，而是 Agent 软件外围的一套状态服务；记忆写入的核心问题不是「选什么存储库」，而是「决定什么时候写」（01:56 / 02:02）
2. 写入链路第一步永远先捕捉事件（Memory Event），而不是马上让模型生成一条记忆；事件保存「发生了什么」及证据来源（用户消息/工具调用结果/任务检查点/外部业务事件），工具调用返回往往比自然语言更适合作为事实来源（03:39）
3. Event 层不可变是数据底线：原始事件保留后，后续 schema/模型变化仍可跟踪、重放、重新派生，也能解释一条记忆为什么生成（04:18）
4. 写入不是「新增文本」，而是结构化操作：新增/更新同一状态/让旧版本退出使用/忽略重复，需在稳定身份 Key 上做合并与并发控制——向量检索只能补充发现，不能承担合并裁决（08:47 / 08:25）
5. 生产级记忆写入系统必须可解释：能回答「为什么出现、为什么没出现、依据哪条证据、经历过哪些操作」，否则不能正式投产（12:31）

### 关键机制
- 双链路架构：在线主链路（消息 → Runtime 组装上下文 → 模型推理 → 响应）与记忆写入链路（Runtime 钩子/工具调用结束/消息队列 → Memory Event → 候选生成策略 → 与旧状态对比 → 明确记忆管理操作 → 事务提交 → 进入事实源；提交后同步更新向量/全文/图索引）（00:34）
- 同步 vs 异步写：同步（下轮马上可见，代价是增加当前响应延迟与复杂度）适用三场景——用户明确说「请记住」、关键任务状态变化（工作流进入下一阶段）、证言状态下轮必须可见；异步（不阻塞主链路，需处理队列延迟/重复投递/失败重试/用户刚说完下轮还没写完的数据不一致）（01:29 / 02:02）；生产实现为混合模式：同步处理明确要求/检查点/关键状态，异步处理普通对话提取/去重/重读（03:02）
- 关键设计原则：同步与异步不是两条不同的写入链路，而是同一条链路的两种执行环境与执行时间点（03:22）
- Memory Event 要素：唯一 Event ID、作用域（scope）、发生时间和来源、原始 Payload 与应用信息、当时的许可和策略上下文（04:00）
- 候选（Candidate）原始化：一条候选尽量只表达一件可独立判断和更新的事；输出不是一段对话摘要，而是多个原始化候选（05:24）
- 记忆类型区分：语义记忆（相对稳定的事实和偏好，如常驻地）、事实记忆（一次发生的经历）、程序记忆（规则、技能、验证过的做法）、任务检查点（工作流恢复所需运行状态）；四类 key 保留周期、冲突规则、存储方式不同（05:32）
- 策略网关五策略 + 三处理状态：Scope（组/用户/智能体/会话/任务 ID——必须由已认证应用运行时注入，不能让模型自己决定写进谁的名下）、价值判断（未来会不会被用/来源是否明确/是否短期情绪）、保存期限（短期 TTL、长期不一定是永久）；处理状态：接受/拒绝/进入复合状态（06:18）
- 执行顺序铁律：确定性权限和合规规则先执行，模型只处理模糊分类和价值判断，不能代替安全边界（07:17）
- 稳定 Memory Key：先做主体（subject）和字段（field）的规范化才能形成稳定 Key；不同记忆类型 Key 策略不同——事件记忆以 Event ID 为主键、任务状态以 Session/Task Key 定位、程序记忆以 Agent ID/Version 定位（07:29 / 07:39）
- 事务提交：Operation ID 保证幂等（同一操作超时重试不产生第二份状态）；乐观锁版本比较（声明基于 version 2 更新，若已被推进到 3 则 CAS 失败重新比对，不静默覆盖）；成功提交同时产出三类结果——权威事实源（当前值 + 历史版本）、操作日志（谁在何时依据什么证据做了什么变更）、Outbox（后续需更新的检索索引清单）（09:49 / 10:21）
- 索引是派生视图：向量/全文/图索引为检索构建的派生数据，可延迟更新，可从事实源与操作日志重建（10:43）
- 写后维护：后台 Worker 消费事件队列与操作日志做重复过滤合并、按 TTL 过期、把多次事件经验沉淀为稳定记忆、模型/schema 变化后重建索引；用户纠正/删除也应生成确定性 Memory 操作，走同一管线检查、提交与索引更新（11:12 / 11:31）
- 可观测性：Event ID → Candidate ID → Operation ID → Memory ID → 版本串成全链路 trace；指标三组——质量（写入准确率/漏写率/重复率/冲突解决率）、安全（跨用户泄漏/敏感信息/误写/删除不完整）、运行（P95 写入延迟/队列积压/重试率/索引同步延迟）（11:47 / 12:00）

### 可操作细节
- 七个自检问题：触发在哪里？Scope 从哪来？Candidate 的 Schema 是什么？稳定的 Key 是什么？写入前怎么检查旧状态？支持哪些操作？事实源/幂等/版本/索引与 Trace 怎么落地？（13:41）
- 完整七步示例（用户「我搬到上海」）：Event 捕获 → Candidate 生成 → Policy Gate 确认归属与保存许可 → 身份解析（自然语言翻译为稳定 Key）→ 按同 Scope+Key 查当前值 → Reconciler 生成操作（上海 version3、北京 version2 从今天起失效，前提是当前版本仍为 2）→ 事务写入器用 Operation ID 幂等 + 版本比较，提交事实源与操作日志，经 Outbox 更新向量/全文/图索引（12:32）
- 四个核心对象：Memory Event（发生了什么 + 证据）、Memory Candidate（可能值得写什么）、Committed Memory（范围/来源/时间/版本的最终状态）（13:27）
