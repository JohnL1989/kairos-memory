## ADR-001：双模式存储——SQLite 优先落地，PostgreSQL 为标准形态

**决策状态：** 已采纳
**设计状态：** 进行中

### 背景

系统需要一个支持并发读写、备份恢复和远程访问的数据库引擎。同时，个人开发与单机部署场景要求零配置起步能力。这两项诉求无法由单一引擎同时最优满足。

### 备选方案

| 方案 | 优势 | 劣势 |
|:----|:-----|:-----|
| 仅 SQLite | 零配置，嵌入式，文件级备份 | 单实例单写入，不满足多客户端并发与远程访问需求 |
| 仅 PostgreSQL + pgvector | MVCC 并发，WAL 备份，向量检索 | 需要独立服务进程，个人场景部署门槛高 |
| **双模式（本决策）** | 起步零依赖 + 目标形态可扩展，由抽象层屏蔽差异 | 需维护两套方言适配与一致性验证 |

### 决策

采用**双模式存储**，以 `StorageBackend` 抽象层屏蔽差异：

| | 引擎 | 定位 | 交付顺序 |
|:--|:--|:--|:--|
| **轻量模式** | SQLite + sqlite-vec | **起步形态**——零配置、嵌入式，v0.1.0 首迭代载体 | 首迭代（2026-07-31 竖切决策） |
| **标准模式** | PostgreSQL + pgvector | **目标形态**——MVCC（读不阻塞写）、WAL（增量备份）、pgvector（路径内向量检索），支撑独立服务架构下的并发与远程访问 | 竖切验收后适配 |

两种模式并非「主选 / 备选」关系，而是**同一抽象接口下的两个并存实现**：业务代码只依赖 `StorageBackend` 契约，切换后端仅需变更配置中的后端标识。

### 附加考虑

- **模式选择准则**：单机个人使用、CI/测试环境 → 轻量模式；多客户端并发、远程访问、需要在线备份 → 标准模式。
- **一致性责任**：两种模式的行为差异（如全文检索实现，见 [data-model.md](../specification/data-model.md)）必须在数据模型文档中显式登记，不得以「等价替换」一笔带过。
- **迁移工具**：两模式共用 Alembic 版本链（见 [ADR-011](#adr-011迁移工具选择-alembic)）。

### 否决方案分析

- **仅 SQLite**：单实例单写入不满足服务架构的并发需求。即使使用 WAL 模式，写入仍受限于单连接——因此 SQLite 不能作为**唯一**后端，但完全胜任首迭代与个人部署场景。
- **仅 PostgreSQL**：强制引入独立服务进程，与「个人开发零依赖起步」目标冲突，且会阻塞首迭代竖切验证。

## ADR-002：用 events 数据库表而非消息队列

**决策状态：** 已采纳
**设计状态：** 进行中

### 背景

组件间异步通信（升华阶段触发、事件协调）需要可靠传递机制。

### 备选方案

| 方案 | 优势 | 劣势 |
|:----|:-----|:-----|
| Redis Pub/Sub | 低延迟，内存级，成熟 | 额外进程，数据丢失风险 |
| RabbitMQ | 持久化，ACK 确认 | 运维复杂度高，单机场景过重 |
| NATS | 轻量消息队列 | 单机起额外进程，运维成本 > 收益 |
| 数据库表（events） | 零外部依赖，事务一致 | 不支持持久队列的高级路由 |

### 决策

采用数据库表 events。原因：v0.1.0 单机部署，无需消息中间件。数据库表足够可靠，且利用现有事务边界保证一致性。

### 否决方案分析

NATS 否决：单机起额外进程，运维成本 > 收益。

## ADR-003：四条公理而非「三个自主」作为第一性原理

**决策状态：** 已采纳
**设计状态：** 已定稿

### 背景

系统的第一性原理应该从「使用方式」出发而非「系统能力」出发。需要最底层的逻辑起点。

### 备选方案

| 方案 | 优势 | 劣势 |
|:----|:-----|:-----|
| 三个自主（自主管理/思考/进化） | 方向宏大，易于理解系统能力 | 回答了「系统能做什么」，没回答「为什么这样做」 |
| 四条公理（使用/契约/组织/升华） | 底层逻辑推导，组件可回溯 | 抽象度高，新读者门槛更高 |

### 决策

采用四条公理。理由：「用」定义了「存」——使用契约是比系统能力更底层的认知。「三个自主」是功能目标的集合，公理是底层逻辑的推导。

> **分层定位：** 四条公理与 [cognitive-foundation.md](../foundation/cognitive-foundation.md) 的「记忆即使用」第一性原理不冲突。前者是**架构设计推理公理**（回答「设计决策从何推导」），后者是**认知价值层第一性原理**（回答「系统为何存在、以什么为衡量」）。认知基础 P1–P6 设计原则是两者在架构约束层的交汇——将价值主张转化为可验证工程约束，同时体现四条公理的推导路径。

### 否决方案分析

三个自主否决：回答了「系统能做什么」，没回答「为什么这样做」。组件之间缺乏推导链条，是并排放置的。

## ADR-004：路径空间作为一级检索手段而非纯向量搜索

**决策状态：** 已采纳
**设计状态：** 进行中

### 背景

Agent 需要确定性定位能力而非概率匹配。纯向量搜索的「不确定性」导致找同类知识时每次结果不一致。

### 备选方案

| 方案 | 优势 | 劣势 |
|:----|:-----|:-----|
| 纯向量搜索 | 语义理解强，无需手动组织 | 全库概率匹配，无法隔离不同领域上下文 |
| 混合搜索（向量 + 全文） | 结合语义和精确匹配 | 复杂度高，仍然以概率为主 |
| 全文搜索优先 | 确定性返回 | 语义理解弱 |
| 路径空间 + 向量辅助 | 确定性定位 + 路径内语义检索 | 需要手动组织路径 |

### 决策

采用路径空间作为第一检索手段，向量搜索退化到路径内辅助定位。路径边界提供确定性隔离，路径间不存在概率匹配。

### 否决方案分析

纯向量否决：全库概率匹配无法隔离不同领域上下文——搜索「用户偏好」时可能返回「项目规则」的内容。

### 修订说明（RC-06）

本 ADR 与 [architecture-v0.1.0.md](../foundation/architecture-v0.1.0.md) §7.3a 三信号混合检索经复审（RC-06）澄清后确认**无实质张力**，此前仅是文档表述引起误解：

- 「路径空间作为第一检索手段」= 路径是**硬过滤边界**（先按路径前缀圈定候选域），不是第四路信号；
- 「向量搜索退化到路径内辅助定位」= 向量的**作用域被路径限制**（仅在域内参与排序），**不是权重降低**——语义向量仍是三信号中权重最大的主信号（α_s=0.50）；
- 本 ADR 否决的「混合搜索（向量+全文）」指**未加路径过滤的全库概率混合**，而 §7.3a 的三信号排序发生在路径已过滤的域内，二者不冲突。

> 检索管线的两阶段结构已在 §7.3a 开头显式说明。

## ADR-005：四类契约而非单一种类记忆

**决策状态：** 已采纳
**设计状态：** 进行中

### 背景

不同类型的记忆使用方式完全不同——有些需要每 session 预加载，有些需要时才召回，有些仅在特定条件下激活，有些用完即焚。不能同一种管法。

### 备选方案

| 方案 | 优势 | 劣势 |
|:----|:-----|:-----|
| 单种记忆 + 过滤标签 | 数据模型简单 | 标签可以分类但无法定义使用行为 |
| 四类契约 | 每种记忆有完整生命周期定义 | 数据模型和调度逻辑更复杂 |

### 决策

采用四类契约（常驻/按需/环境/临时）。理由：契约定义了完整的生命周期——加载方式、成本结构、修改权限、隔离规则。标签做不到这些。

### 否决方案分析

单种+标签否决：标签可以分类但无法定义使用行为。「同一种数据 + 不同标签」不能解决「常驻契约要冻结快照、临时契约要写完即焚」的问题。

## ADR-006：升华层空闲驱动而非定时 cron

**决策状态：** 已采纳
**设计状态：** 进行中

### 背景

后台处理（升华、压缩、归档）不应占用推理资源。固定时间调度可能撞上推理高峰。

### 备选方案

| 方案 | 优势 | 劣势 |
|:----|:-----|:-----|
| 定时 cron（如 Aion 的 Compactor 05:00） | 时间固定，可预测 | 固定时间可能撞上推理高峰 |
| 空闲驱动 | 保证推理优先，不抢资源 | 空闲不足时升华延迟 |

### 决策

采用空闲驱动的三优先级调度。升华层仅在低优先级队列（系统完全空闲时）执行。调度器通过负载感知判断推理状态。

### 否决方案分析

定时 cron 否决：固定时间撞上推理高峰时，后台操作抢占推理资源，影响用户体验。

## ADR-007：单外部 Provider 而非多 Provider 并发

**决策状态：** 已采纳（v0.1.0 默认单 Provider，多 Provider 配置就绪但默认关闭；加权/Fallback 为 v1.1+）
**设计状态：** 已定稿

### 背景

多个外部记忆 Provider 可能同时提供上下文。同一用户的偏好可能在两个 Provider 中有不同描述，LLM 不知道该信谁。

### 备选方案

| 方案 | 优势 | 劣势 |
|:----|:-----|:-----|
| 允许多 Provider 并发 | 信息来源更广 | 冲突上下文无法裁决 |
| 单 Provider 显式切换 | 确定性来源，无冲突 | 切换需要配置变更 |

### 决策

采用单 Provider 模式。同一时间只允许一个外部 Provider 生效。切换通过显式配置变更完成，不支持运行时并发。

> **v0.1.0 实现说明：** 运行时可配置单 Provider，切换需显式配置变更重启生效。架构 [architecture-v0.1.0.md](../foundation/architecture-v0.1.0.md) §3.2 描述的多 Provider 冲突消解协议为 v1.1+ 演进预留——v0.1.0 仅实现单 Provider 模式，多源校准信号冲突消解不在 v0.1.0 范围内。

### 否决方案分析

多 Provider 否决：冲突无框架级解法。LLM 面对冲突信息来源无法裁决哪个更可信。

## ADR-008：SOUL.md 不自动修改

**决策状态：** 已采纳
**设计状态：** 已定稿

### 背景

最高行为准则（SOUL 文档）的修改涉及系统行为边界的改变。是否允许系统自主修改？

### 备选方案

| 方案 | 优势 | 劣势 |
|:----|:-----|:-----|
| 允许系统直接修改 SOUL.md | 完全的自主进化 | 破坏可审计性和行为可预测性 |
| 人工审核后修改 | 可审计、可控制 | 需要人工介入 |

### 决策

SOUL.md 不自动修改。最高行为准则的修改需人工审核。可审计性 > 完全自主。SOUL 是人与 Agent 的契约，不是系统的产物。

### 否决方案分析

自动修改否决：破坏可审计性和行为可预测性。系统可能在不被注意的情况下改变自己的行为边界。

## ADR-009：用异步预取优化按需召回延迟

**决策状态：** 已采纳
**设计状态：** 进行中

### 背景

语义召回的 LLM 侧调用可能增加感知延迟。用户等待召回结果时模型已开始生成。

### 备选方案

| 方案 | 优势 | 劣势 |
|:----|:-----|:-----|
| 同步召回，模型等待 | 实现简单 | 召回时间叠加到用户感知延迟上 |
| 异步预取 | 召回延迟隐藏在推理过程中 | 预取可能取到不需要的内容 |

### 决策

采用异步预取。查询提交后立即开始语义召回，召回与模型生成并行。结果是模型需要时已就绪，不增加感知延迟。

### 否决方案分析

同步召回否决：召回时间叠加到用户感知延迟上，用户体验差。

## ADR-010：参数化记忆为可选非默认路径

**决策状态：** 已采纳
**设计状态：** 已定稿

### 背景

高频使用的策略可以通过参数化（模型内化）实现零延迟访问。但模型内化不可审计、不可迁移、换模型需重新训练。

### 备选方案

| 方案 | 优势 | 劣势 |
|:----|:-----|:-----|
| 默认走参数化 | 零延迟访问 | 不可审计、不可迁移 |
| 默认走外化（文件/数据库） | 可控、可审计、可迁移 | 每次加载需要 IO |
| 外化为主，参数化为可选升级路径 | 两者优势可兼得 | 需要两套机制 |

### 决策

采用外化为主、参数化为可选第四阶段升级路径。默认走外化保持可控可审计可迁移；参数化为可选路径，需要超长期验证（连续 30 天无冲突）后才可导出。

### 否决方案分析

默认参数化否决：不可审计、不可迁移、换模型需重新训练。

## ADR-011：迁移工具选择 Alembic

**决策状态：** 已采纳
**设计状态：** 已定稿

### 背景

`data-model.md` 定义 `schema_version` 表、错误码 `ERR-DB-002` 定义「数据库迁移失败」、`kairos db migrate` / `kairos db migrate rollback` 已写入 runbook 与 troubleshooting，但全库此前未选定迁移工具——三处定义悬空，无法落地。

### 备选方案

| 方案 | 优势 | 劣势 |
|:----|:-----|:-----|
| **Alembic（本决策）** | SQLAlchemy 生态，同时支持 SQLite / PostgreSQL 双模式；原生 `downgrade()` 直接支撑 `kairos db migrate rollback` | 引入 SQLAlchemy 依赖；FTS5 虚拟表 autogenerate 不识别，需手写 `op.execute()` |
| 自研轻量迁移器 | 完全可控，可针对 FTS5 虚拟表定制 | 需自行处理两方言差异与回滚逻辑，维护成本高 |
| 暂不选型 | 零 | 三处已有定义持续悬空 |

### 决策

采用 **Alembic** 作为双模式共用迁移工具：

- **双模式支持**：Alembic 运行于 SQLAlchemy 之上，`StorageBackend` 抽象层若基于 SQLAlchemy（`src/storage/models.py`），Alembic 天然配套，同时生成 SQLite 与 PostgreSQL 两种方言的迁移脚本。
- **回滚原生支撑**：`kairos db migrate rollback` 映射到 Alembic `downgrade()`，无需自研回滚逻辑。
- **与 ADR-001 契合**：双模式存储由 `StorageBackend` 抽象层屏蔽差异，Alembic 版本链两模式共用。
- **FTS5 例外处理**：`memories_fts` / `skills_fts` 为 FTS5 虚拟表，Alembic autogenerate 不识别，相关 DDL 以手写 `op.execute()` 纳入迁移版本链（详见 [data-model.md](../specification/data-model.md) §11）。
- **版本表协同**：现有 `schema_version` 表（[data-model.md](../specification/data-model.md) §11）记录 schema 版本号、迁移名与校验和；Alembic 默认 `alembic_version` 表可与 `schema_version` 协同——以 `schema_version` 为权威版本源，`env.py` 读取其 `version` 作为 Alembic 当前头，避免双版本源漂移。

### 否决方案分析

- **自研轻量迁移器否决**：需重复实现方言差异处理与回滚，维护成本高于引入成熟 Alembic；且与 ADR-001 的 SQLAlchemy 抽象层方向不一致。
- **暂不选型否决**：`ERR-DB-002`、`kairos db migrate` 等已定义但无工具承接，属于虚假已定义状态，必须闭合。

## ADR-012：向量线性投影固定正交投影 + 矩阵随 schema 持久化

**决策状态：** 已采纳
**设计状态：** 已定稿

### 背景

轻量模式使用 BGE-M3 原生产出 **1024 维**向量，需映射至 **1536 维**以与标准模式（text-embedding-3-small，原生 1536 维）保持同一向量空间（全库 7 处口径一致）。此前无任何文档定义该投影**怎么来、存哪、不同模式向量能否互比**——若矩阵不持久化，重启后重新随机生成会使全部历史向量失效（数据损坏级风险）。

### 备选方案

| 方案 | 优势 | 劣势 |
|:----|:-----|:-----|
| 训练式投影（学习型映射） | 可能更优的检索质量 | 需训练数据/目标函数，且两模式向量空间更可能漂移，端云同步复杂度高 |
| 随机正交投影（本决策） | 零训练成本；正交化近似保能量；矩阵可冻结并随 schema 版本发布 | 不保证余弦相似度严格保序，轻量模式融合权重需单独标定 |
| 不投影（轻量模式降为 1024 维独立空间） | 最简单 | 与标准模式 1536 维向量无法互比，端云同步/模式迁移场景失效 |

### 决策

采用**固定随机正交投影** $W \in \mathbb{R}^{1536 \times 1024}$，并随 schema 版本冻结持久化：

- **矩阵生成**：一次性随机生成后做正交化（QR），结果**不再随数据训练、不在运行时随机重生成**。
- **持久化位置**：矩阵作为**迁移捆绑资产**随 schema 版本发布，存于 `migrations/0010_embedding_projection.bin`（1536×1024 `float32` 小端 = 6,291,456 字节），由 Alembic 迁移 `0010` 一并写入并打 SHA-256 校验和；**不**作为运行时可写表。
- **版本绑定**：矩阵版本与 `schema_version` 绑定。模式迁移（轻量↔标准）或矩阵版本升级时，须对存量向量执行重投影并写入新列/新表，**禁止原地覆盖**。
- **跨模式互检索**：轻量模式投影后的 1536 维向量与标准模式原生 1536 维向量同处一空间但来源不同，`sync_queue` 端云同步与模式迁移场景下可直接比对余弦距离；矩阵版本不一致时须先对齐矩阵版本。
- **权重标定**：$\alpha_s = 0.50$ 基于标准模式原生 1536 维调参，轻量模式投影后由 `KAIROS_LITE_PROJECTION_CALIBRATION`（见 [configuration.md](../ops/configuration.md) §6.1）控制是否沿用该权重或回退至 BM25 主导路径，v0.1.0 实现期标定。

### 否决方案分析

- **训练式投影否决**：引入训练依赖与两模式向量漂移风险，违背「轻量模式零额外训练」目标。
- **不投影否决**：使轻量/标准模式向量空间割裂，直接破坏端云同步与模式迁移能力，代价高于投影本身的近似误差。

> 投影矩阵存储规格见 [data-model.md](../specification/data-model.md) §13.5。

## 决策历史条目四元组（外部实证参考：PAPER-04 SkillHone）

> **外部实证**：SkillHone PAPER-04——决策历史若只记「改了什么」而不记「为什么改、依据什么、结果如何」，回溯时无法区分「正确演进」与「试错漂移」；证据若不可复查，决策链等同无证。本格式补充决策记录（ADR 条目之外）的增量修订记录规范。

决策历史条目统一为四元组——**诊断 / 修订 / 证据 / 结果**：

| 元组 | 内容 | 要求 |
|:--|:--|:--|
| **诊断**（Diagnosis） | 触发本次决策修订的问题/差距描述 | 可回溯到问题来源（审计批次、告警、债务编号） |
| **修订**（Revision） | 本次修订的具体内容与影响范围 | 指向修订落点（文档 §章节 / 代码路径） |
| **证据**（Evidence） | 支撑本次修订的依据 | **指向见证锚定副本**——证据必须是可复查的锚定记录（`witness_anchor` 对应条目，见 [data-model.md](../specification/data-model.md) §3；或外部实证来源/审计批次记录），非口头理由 |
| **结果**（Outcome） | 修订后的可验证结果/预期 | 可验证或可证伪（验收判据 / 监控指标） |

**应用范围**：ADR 正文条目（背景/备选/决策/否决）之外的增量决策修订——D-xx 裁决、勘误、审计处置——在 changelog 批次条目与债务闭环记录中按四元组补全；既有条目不强制回填，新条目自本批次起执行。
